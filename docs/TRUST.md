# Subprocessors and encryption

Generated by `npm run trust:doc` from `lib/processors.ts` and `lib/encryption.ts` (phase 16, step C7c). Don't edit by hand; a test compares them. Settings › Security › Subprocessors and encryption shows the same.

## Subprocessors

Every outside service that receives customer data, what it receives, and what a deletion does there.

| Service | Receives | When | Keeps | On deletion |
|---|---|---|---|---|
| Twilio | Text messages sent and received, and calls (their recordings when recording is on) | SMS and voice channels | Message records and recordings, until deleted | Deleted by Relay |
| Anthropic (Claude) | Customer messages Zoe answers, with personal data redacted when the setting is on | Zoe, the AI agent | Under Anthropic's API data retention terms | Kept by the provider under its own terms |
| Cloudflare Workers AI | Knowledge content to embed, customers' questions to search it with, and call audio to transcribe | Zoe's knowledge search, and call transcription | Nothing after answering | Not kept |
| Amazon SES | Emails Relay sends to customers | Email channel | Sending and delivery events under Amazon's terms (not the email's content once delivered) | Kept by the provider under its own terms |
| Meta (WhatsApp, Instagram, Messenger) | Messages sent and received on those channels | WhatsApp, Instagram and Facebook Messenger channels | Under Meta's terms; messages stay in the customer's own app | Kept by the provider under its own terms |
| Slack and Discord | Messages in the workspace's connected community spaces | Slack and Discord channels | In the workspace's own Slack or Discord | The workspace's own destination |
| The workspace's webhooks | Event payloads for the topics each webhook subscribes to | Settings › Developers › Webhooks | In the workspace's own systems | The workspace's own destination |
| The workspace's data connectors and apps | The inputs each connector declares, and what installed apps read through the API | Zoe's data connectors, Canvas and OAuth apps | In the workspace's own systems or the app's | The workspace's own destination |
| Google Safe Browsing | The web addresses in customers' messages and emails (nothing else) | Link safety, when Relay is deployed with a Safe Browsing key | Under Google's Safe Browsing terms | Kept by the provider under its own terms |
| Cloudflare and Neon (Relay's hosting) | Everything Relay stores: the database, files and queued work | Always | Deleted with the person; PostgreSQL's point-in-time backups keep them until the backup window passes | Deleted by Relay |

## How data is protected

| What | How |
|---|---|
| Everything in transit | Every connection to Relay uses HTTPS (TLS). Relay reaches its database through Cloudflare Hyperdrive over TLS, and calls providers and your systems only at https addresses. |
| Stored data | The database (PostgreSQL at Neon) and files (Cloudflare R2) are encrypted at rest by those providers, with keys they manage. |
| Credentials and secrets you give Relay | Channel and connector credentials, app and webhook secrets, single sign-on client secrets, two-factor secrets and invitation links are sealed with AES-256-GCM: a new random 96-bit nonce each time, bound to the workspace and purpose (so a sealed value can't be moved elsewhere), under RELAY_CONNECTOR_KEY. The API never returns them. |
| Messenger identity keys | Each workspace's keys for verifying signed-in users are wrapped with AES-256-GCM under IDENTITY_MASTER, bound to the workspace and key id. |
| Teammates' passwords | Kept only as scrypt hashes (N=2^15, r=8, p=1) with a random 16-byte salt per password, and compared in constant time. |
| Session, API and sign-in tokens | Kept only as SHA-256 hashes: teammate and support sessions, API and app tokens, invitations, two-factor and single sign-on logins, and workflow webhook secrets. A token is shown once and can't be read back. |
| What Relay signs | Webhook deliveries and Canvas requests carry an HMAC-SHA-256 signature with a timestamp; deletion certificates are signed with HMAC-SHA-256 under a key derived from RELAY_CONNECTOR_KEY. |

## Keys

Each is a deployment secret, set with `wrangler secret put`: never in code, configuration or logs.

| Key | Protects | Rotation |
|---|---|---|
| `RELAY_CONNECTOR_KEY` | Seals credentials and secrets; signs deletion certificates. | Not automated yet: changing it makes sealed credentials unreadable, so each one has to be entered again. Webhook and Canvas secrets rotate on their own, with a grace period for the old one. |
| `IDENTITY_MASTER` | Wraps each workspace's messenger identity keys. | Each workspace rotates its own identity keys through two slots without downtime. Changing IDENTITY_MASTER itself isn't automated yet. |
| `SESSION_SECRET` | Signs the messenger's short-lived session tokens and preference links. | Changing it signs everyone out of the messenger, who then sign in again as before. |
| `RELAY_BRIDGE_SECRET` | Signs each request from Relay's web host to its API. | Set the new value on the web host and the API together: a request signed with the old one is refused (each proof lasts 30 seconds). |
